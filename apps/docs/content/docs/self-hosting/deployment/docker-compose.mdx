## Prerequisites

Before starting, ensure you have:

- [Docker](https://docs.docker.com/get-docker/) 20.10 or later
- [Docker Compose](https://docs.docker.com/compose/install/) v2.0 or later
- SMTP credentials for sending emails
- At least 2GB of available RAM
- A domain name (for production deployments)

Verify your installation:

```bash
docker --version
docker compose version
```

## Docker Compose File Overview

esign uses an embedded SQLite database (Hanzo Base) — a single shared `sign.db`
file with tenancy enforced at the query layer (see HIP-0305), not a separate
database server. The production `compose.yml` is therefore a single service whose
data lives on a named volume mounted at `BASE_PATH`:

```yaml
name: hanzo-sign-production

services:
  hanzo-sign:
    image: hanzo-sign/hanzo-sign:latest
    environment:
      - BASE_PATH=/opt/hanzo-sign/base/data
      - DATABASE_URL=file:/opt/hanzo-sign/base/data/_dev/sign.db
      # See environment configuration below
    ports:
      - ${PORT:-3000}:${PORT:-3000}
    volumes:
      - base-data:/opt/hanzo-sign/base/data
      - /opt/hanzo-sign/cert.p12:/opt/hanzo-sign/cert.p12:ro

volumes:
  base-data:
```

| Service      | Purpose                                                                 |
| ------------ | ----------------------------------------------------------------------- |
| `hanzo-sign` | Main application container; its SQLite database lives on the `base-data` volume |

There is no separate database container to wait for — the database is a file on
the `base-data` volume, created and migrated automatically on first start.

<Callout type="warn">
  The `base-data` volume must be persistent. If you point `BASE_PATH` at
  ephemeral container storage, all data is lost when the container is recreated.
</Callout>

## Environment Configuration

Create a `.env` file with the following variables:

### Required Variables

```bash
# Database (embedded Base SQLite on the base-data volume)
BASE_PATH=/opt/hanzo-sign/base/data
DATABASE_URL=file:/opt/hanzo-sign/base/data/_dev/sign.db

# Application secrets (generate with: openssl rand -base64 32)
NEXT_PRIVATE_AUTH_SECRET=your-nextauth-secret
NEXT_PRIVATE_ENCRYPTION_KEY=your-encryption-key-min-32-characters
NEXT_PRIVATE_ENCRYPTION_SECONDARY_KEY=your-secondary-key-min-32-characters

# Public URL where Hanzo eSign is accessible
NEXT_PUBLIC_WEBAPP_URL=https://sign.example.com
NEXT_PRIVATE_INTERNAL_WEBAPP_URL=http://localhost:3000

# Email configuration
NEXT_PRIVATE_SMTP_TRANSPORT=smtp-auth
NEXT_PRIVATE_SMTP_HOST=smtp.example.com
NEXT_PRIVATE_SMTP_PORT=587
NEXT_PRIVATE_SMTP_USERNAME=your-smtp-username
NEXT_PRIVATE_SMTP_PASSWORD=your-smtp-password
NEXT_PRIVATE_SMTP_FROM_NAME=Hanzo eSign
NEXT_PRIVATE_SMTP_FROM_ADDRESS=noreply@example.com
```

### Optional Variables

```bash
# Application port (default: 3000)
PORT=3000

# Signing certificate (see Signing Certificate section)
NEXT_PRIVATE_SIGNING_PASSPHRASE=your-certificate-password

# Disable public signups
NEXT_PUBLIC_DISABLE_SIGNUP=false
```

<Callout type="info">Generate secure secrets using: `openssl rand -base64 32`</Callout>

For the complete list of environment variables, see [Environment Variables](/docs/self-hosting/configuration/environment).

### Generating Secrets

Generate the required secrets:

```bash
# Generate NEXT_PRIVATE_AUTH_SECRET
echo "NEXT_PRIVATE_AUTH_SECRET=$(openssl rand -base64 32)"

# Generate encryption keys
echo "NEXT_PRIVATE_ENCRYPTION_KEY=$(openssl rand -base64 32)"
echo "NEXT_PRIVATE_ENCRYPTION_SECONDARY_KEY=$(openssl rand -base64 32)"
```

The embedded SQLite database has no separate user or password to generate — there
is no database server to authenticate against.

## Signing Certificate

A signing certificate is required for document signing. Generate a `.p12` certificate on your host machine and mount it into the container. See [Local Certificate](/docs/self-hosting/configuration/signing-certificate/local) for how to generate one.

Place the certificate on the host and set permissions so the container can read it (UID 1001):

```bash
sudo mkdir -p /opt/hanzo-sign
sudo cp /path/to/your/cert.p12 /opt/hanzo-sign/cert.p12
sudo chown 1001:1001 /opt/hanzo-sign/cert.p12
sudo chmod 400 /opt/hanzo-sign/cert.p12
```

The `compose.yml` mounts this path into the container. Add the passphrase to your `.env` file:

```bash
NEXT_PRIVATE_SIGNING_PASSPHRASE=your-certificate-password
```

If file mounting is not available, you can set `NEXT_PRIVATE_SIGNING_LOCAL_FILE_CONTENTS` with the base64-encoded certificate string instead.

For production deployments that require Adobe Approved Trust List recognition, consider using a [Google Cloud HSM](/docs/self-hosting/configuration/signing-certificate/google-cloud-hsm) or another external HSM.

<Callout type="warn">
  Do not generate or store the signing certificate inside the container. If the container is
  destroyed and rebuilt, or if you run multiple instances, the certificate will be lost or
  inconsistent. Always provide the certificate externally.
</Callout>

## Starting Services

Start all services:

```bash
docker compose --env-file .env up -d
```

Check that containers are running:

```bash
docker compose ps
```

Expected output:

```
NAME                               STATUS    PORTS
hanzo-sign-production-hanzo-sign-1  running   0.0.0.0:3000->3000/tcp
```

Wait for the database file to be created and migrations to complete on first start. Check the logs:

```bash
docker compose logs -f hanzo-sign
```

Look for "Ready" or "Listening on port 3000" in the output.

## Accessing Hanzo eSign

Once the containers are running:

- **Local access**: Open [http://localhost:3000](http://localhost:3000)
- **Remote access**: Use the URL configured in `NEXT_PUBLIC_WEBAPP_URL`

### First Account Setup

Navigate to the signup page and create your account. Verify your email address — if emails are not being delivered, check the container logs for SMTP errors.

<Callout type="info">
  All accounts created through signup are regular user accounts. Admin access must be granted
  directly in the database. Once your accounts are set up, consider disabling public signups by
  setting `NEXT_PUBLIC_DISABLE_SIGNUP=true`.
</Callout>

## Managing Services

### View Logs

View all service logs:

```bash
docker compose logs -f
```

View logs for the application service:

```bash
docker compose logs -f hanzo-sign
```

### Restart Services

Restart all services:

```bash
docker compose --env-file .env restart
```

Restart a specific service:

```bash
docker compose --env-file .env restart hanzo-sign
```

### Stop Services

Stop without removing containers:

```bash
docker compose stop
```

Stop and remove containers (preserves volumes):

```bash
docker compose down
```

Stop, remove containers, and delete data:

```bash
docker compose down -v
```

<Callout type="error">
  Using `down -v` deletes the `base-data` volume — and with it the entire
  `sign.db` database. Back up your data first.
</Callout>

## Production Considerations

### Reverse Proxy

For production, place Hanzo eSign behind a reverse proxy for SSL termination:

**nginx example:**

```nginx
server {
    listen 443 ssl http2;
    server_name sign.example.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

**Caddy example:**

```
sign.example.com {
    reverse_proxy localhost:3000
}
```

### Database Backups

The database is a single SQLite file on the `base-data` volume, so backups are
file snapshots — no `pg_dump`, no replication topology. Use `sqlite3 .backup`
for a consistent copy even while the app is running:

```bash
# Manual backup (consistent online copy, includes the WAL)
docker compose exec hanzo-sign \
  sqlite3 /opt/hanzo-sign/base/data/_dev/sign.db ".backup '/opt/hanzo-sign/base/data/sign-backup.db'"
docker compose cp hanzo-sign:/opt/hanzo-sign/base/data/sign-backup.db ./sign-backup.db

# Restore: stop the app, replace the file, restart
docker compose stop hanzo-sign
docker compose cp ./sign-backup.db hanzo-sign:/opt/hanzo-sign/base/data/_dev/sign.db
docker compose start hanzo-sign
```

See [Backups](/docs/self-hosting/maintenance/backups) for automated backup strategies.

### Resource Limits

Add resource limits to prevent container resource exhaustion:

```yaml
services:
  hanzo-sign:
    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '0.5'
          memory: 512M
```

### No External Datastore Needed

esign's database is embedded — there is no managed PostgreSQL service to attach,
no connection string to rotate, and no separate datastore to scale. Production
durability comes from putting `BASE_PATH` (the `base-data` volume) on reliable,
backed-up block storage and snapshotting it on a schedule. See
[Backups](/docs/self-hosting/maintenance/backups) for volume-snapshot strategies.

<Callout type="warn">
  SQLite is a single-writer database. Run exactly one `hanzo-sign` container that
  owns the `base-data` volume. Do not scale this service to multiple replicas
  pointed at the same file.
</Callout>

### S3 Storage

For high-volume deployments, configure S3-compatible storage:

```bash
NEXT_PUBLIC_UPLOAD_TRANSPORT=s3
NEXT_PRIVATE_UPLOAD_BUCKET=your-bucket
NEXT_PRIVATE_UPLOAD_REGION=us-east-1
NEXT_PRIVATE_UPLOAD_ACCESS_KEY_ID=your-access-key
NEXT_PRIVATE_UPLOAD_SECRET_ACCESS_KEY=your-secret-key
```

See [Storage Configuration](/docs/self-hosting/configuration/storage).

## Troubleshooting

<Accordions type="multiple">
  <Accordion title="Container fails to start">
    Check logs: `docker compose logs hanzo-sign`. Common causes: missing environment variables
    (ensure all required variables, including `BASE_PATH` and `DATABASE_URL`, are in `.env`),
    the `base-data` volume not writable by the app user (UID 1001), port conflict (change `PORT`
    in `.env` if 3000 is in use).
  </Accordion>
  <Accordion title="unable to open database file">
    The directory in `DATABASE_URL` does not exist or is not writable. Confirm the `base-data`
    volume is mounted at `BASE_PATH` and the path is absolute:
    `docker compose exec hanzo-sign ls -la /opt/hanzo-sign/base/data`. Then verify the database:
    `docker compose exec hanzo-sign sqlite3 /opt/hanzo-sign/base/data/_dev/sign.db 'SELECT 1'`.
  </Accordion>
  <Accordion title="Certificate errors">
    Check certificate status: `curl http://localhost:3000/api/certificate-status`. Common issues:
    file not found (verify volume mount in `compose.yml`), permission denied (run `chown 1001:1001`
    on the certificate file), no password (the certificate must have a password).
  </Accordion>
  <Accordion title="Emails not sending">
    Check `NEXT_PRIVATE_SMTP_TRANSPORT` matches your setup, verify host, port, username, and
    password, check logs: `docker compose logs hanzo-sign | grep -i smtp`.
  </Accordion>
  <Accordion title="Application unreachable">
    Verify containers are running: `docker compose ps`; check the port mapping matches your `.env`;
    test locally: `curl http://localhost:3000/api/health`; check firewall rules allow traffic on the
    configured port.
  </Accordion>
  <Accordion title="Out of disk space">
    Check disk usage: `docker system df`. Clean up: `docker system prune -a`.
  </Accordion>
</Accordions>
